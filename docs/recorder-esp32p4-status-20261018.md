## 5. 映像が 60fps に届かない理由(4 倍のとき)

1 フレームの処理は、GBA の 240×160 を色変換して 4 倍に拡大し(YUV420 で 921,600 バイト)、ハードウェアエンコーダに渡す流れ。

| 計測 | 映像 | 備考 |
|---|---|---|
| 録画しないベンチマーク | 毎秒 61.4 フレーム | 拡大 14ms、エンコード 10ms |
| 録画(r108) | 663 フレーム / 33.4 秒 = 毎秒約 20 フレーム | 20 秒で止める合図が遅れ、33 秒回った |

録画中だけ遅くなる理由は 3 つ。

1. **外付けメモリ(PSRAM)の取り合い。** USB の受信、拡大結果の書き込み、エンコーダの読み込みが同時に PSRAM を使う。拡大のうち色変換は、ベンチマークの 6.9ms から録画中は 25.8ms まで延び、PSRAM への書き込み待ちも 18.9ms かかった。
2. **コア 0 の混雑。** USB ホストの処理が CPU の 22〜24% を使い、DMA の完了割り込みもコア 0 に来る。拡大の処理がそのたびに中断され、コア 0 が空かなくなって、見張り役(ウォッチドッグ)が警告を出す。
3. **内部 RAM の不足。** エンコーダは内部 RAM にひと続きの約 69KB を要る。DMA の作業領域などと取り合いになり、録画が始まらなかったり、SD への書き込みが「メモリ不足」で失敗したりした。

試して効かなかったこと: PPA(拡大がバイリニア補間になり、ドットが崩れる)、色変換の表引き(256KB 版も 1.5KB 版も録画中は速くならない)、DMA の同時発行を 2 から 4 に増やす。

## 6. 480×320 方式の現状(10/18 にユーザーが決定)

- 録画機は 480×320 で録り、PC で `recorder/tools/upscale_x2.bat` を使ってドットのまま 2 倍(960×640)にする。
- 480×320 なら、YUV420 の色 1 つがちょうど GBA の 1 ドットに当たるので、色がにじまない。データ量は 4 倍のときの 4 分の 1。
- コミット済み(7d60410): 既定値を 2 倍・8Mbps に変更。2 倍専用の拡大処理を追加。NVS に残っている 4 倍の設定を 2 倍へ移す処理も入れた。
- 未コミットの変更が `recorder/main/video_enc.c` に残っている。2 倍のときは DMA の作業領域を作らない変更。効果はまだ確かめていない。
- 録画はまだ通っていない。最後の試験(rec94)では、次の 2 点が起きた。
  - 起動直後の内部 RAM の空きは 429KB。エンコーダの起動時の準備で 264KB 減り、録画を始めた時点では 83KB しか残っていない。480×320 でこれほど使うのはおかしい。4 倍の大きさで確保しているか、エンコーダの部品が内部 RAM を使う作りになっている疑いがある。
  - 拡大の処理(scale_a)がコア 0 を独り占めしてウォッチドッグが出た。2 コアに分けた作りの残りで、2 倍のときは作られない相方を待ち続けている疑いがある。

## 7. 課題(優先順)

1. **480×320 で 20 秒の録画を通す。**
   - エンコーダの起動時の確保が 264KB になる原因を突き止め、480×320 の大きさにする。
   - 2 コアに分けた作りを外し、拡大は 1 本の処理に戻す。
   - 未コミットの `video_enc.c` の変更を確かめてコミットする。
2. 録画できた mp4 を `upscale_x2.bat` で変換し、ドットがそのまま並ぶか目で確かめる(バッチは試験用の動画でしか試していない)。
3. 段階 B〜D を進める。MSC の往復を通しで試す。ボタンと LED を実機で確かめる。手順書を 480×320 前提に書き直す。
4. 試験用に入れたものを片づける。
   - 調査用のコードを製品のファームから外すか、別ビルドに分ける。PPA の試験(`ppa_probe.c`)、SD の生セクタ試験、診断用の 1 文字コマンドがこれに当たる。
   - 試験用に入れた設定を戻す。ヒープポイズニングが一番重い設定(COMPREHENSIVE)のままで、メモリの確保と解放のたびに遅くなる。録画中の速さに響いている可能性もある。
   - コメントの日付が「2026-10-19」になっている(正しくは 10-18)。「監督指示」と書いたコメントも外す。
5. `recorder/tools/` は `.gitignore` の対象なので、`upscale_x2.bat` はリポジトリに入っていない。残すなら置き場所を変える。
6. 古い microSD は、書き込みが成功と返るのに内容が残らない故障品だった。捨てるか、使わない印を付ける。

## 8. 進みが遅かった理由

- Qwen の 1 ステップは 10〜60 秒かかり、1 つの手を入れて結果が出るまでに 20〜30 分かかった。
- 文脈の圧縮が 1 回約 9 分で、作業時間の 2 割を占めた。
- 調べ物に寄り道しがちで、監督が割り込みで方向を戻す場面が多かった(PPA の調べ物、ESP-IDF の内部コードの読み込み、ログの読み返しなど)。
- 監督(Claude)の判断ミスで回り道した分もある。FAT が壊れているという見立て(実際はカードの故障)、DMA 化(内部 RAM を食い、録画中は速くならなかった)、2 コアへの分割(途中で方式を変えた)。

## 9. 2026-10-18 夜の続き(Claude が実機で作業)

### 結果

- **480x320 の 20 秒録画が通った**(REC_0013: 映像 1211 枚 / 20.27 秒 = 59.7fps、音声 635 枚 / 20.29 秒、取りこぼし 0、ウォッチドッグなし)。
- mp4 を PC で検査: avc1 480x320、mp4a 32000Hz、映像と音声の長さが一致。`upscale_x2.bat` で 960x640 にしてドットがそのまま並ぶことを目で確認した。
- 2 倍ベンチ(nano 停止中): 拡大 5.0ms/枚(表引き 2.9 + 書き出し 2.1)、エンコード 3.0ms → 134.5fps。

### 遅かった本当の理由

- USB ホスト(HS の割り込み 1 万回/秒 + usbh タスク)が **core0 の 6〜7 割**を使う。同じ core0 に置いた拡大は 2.5 倍遅くなり(2 倍で 9.7ms → 24.8ms/枚)、core0 が 100% になって main も IDLE0 も止まっていた。5 章の「PSRAM の取り合い」は主因ではなかった。
- core1 では rx の復号(1 ライン 19us)と AAC(1 枚 11ms × 47 回/秒 ≒ core1 の半分)が重かった。

### 入れた対策

| 対策 | 効果 |
|---|---|
| nano のサンプル → (Y,U,V) の直引き表(96KB、internal)。rx は復号をやめて memcpy だけ | 拡大の rgb 7.0 → 2.9ms/枚、rx 20% → 8% |
| 拡大タスクを core1 の prio3 へ(core0 は USB だけ) | core0 の飽和が解消、main が毎秒回る |
| 2 倍でも PSRAM 書き出しを GDMA(段 11,520B × 4) | 拡大の CPU 2.6ms/枚ぶんを DMA へ |
| AAC を 48kHz → 32kHz(nano の実レート 32802Hz とほぼ 1:1) | AAC の仕事 2/3。音声の取りこぼし 0 |
| USB 受信リングの起こし方を 1ms まとめ読みに(毎パケットのコア間割り込みをやめた) | rx 16% → 8% |
| ヒープポイズニング(COMPREHENSIVE)を無効化 | 試験用設定の撤去 |
| 2 コア分割の残骸を削除、日付と「監督指示」の表記を修正 | 整理 |

録画中の CPU(2026-10-18 t5): core0 = usbh 39% + IDLE0 57%、core1 = scale 28% + aac 22% + rx 8% + mux 3% + enc 2% + IDLE1 34%。

### 960x640 を基板で直接録ることについて

CPU の総量で見ると、USB ホスト 65% + 拡大(4 倍で約 8ms × 60 = 48%)+ AAC 33% + rx 8% + mux/enc 5% ≒ 160%(2 コアで 200%)で数字の上では入るが、USB は core0 から動かせず、core0 に拡大を同居させると 2.5 倍遅くなる実測がある。PSRAM の流量も 4 倍になる。現実的には **nano 側で 1 ラインを 512 バイト詰め(484 + 詰め物)にして USB の転送回数を 1/10 以下にする**変更が先で、それで core0 が空けば 960x640 を試す価値がある。nano の FW は今は触らない方針なので、480x320 + PC で 2 倍を本線とする。

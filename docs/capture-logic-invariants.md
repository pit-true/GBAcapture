**2026-07-08 ユーザー承認により確定。** 以降、ここに書かれた設計を変更する場合は

## 映像

| # | 不変条件 | 破った場合の症状 |
|---|---|---|
| V1 | 1ライン周期 = **DCK 241パルス**（ジャンク1 + 可視240）。読み出しは各周期の**+1オフセット**から240個 | 対角線ノイズ / 左端に白線 |
| V2 | 1フレーム = **161バースト**（VBLANK中のダミー1 + 可視160）。ダミーにSPLは無い | 映像が1ライン+α巻き取られてズレる |
| V3 | DMAは**サーキュラモードで'S'時に1回だけアーム**。ライン毎の再アーム禁止 | 行ごとの水平ジッタ |
| V4 | フレーム同期は**ハイブリッドアンカー**: 列位相=VBLANKストール検出（250µs無進行）、ライン0特定=フレーム先頭SPLのリング位置から241の整数倍で補正 | V2の症状 / 列ズレ |
| V5 | リングサイズは**241の倍数**（現在7712=241×32） | ラインがリング境界をまたぎ壊れる |
| V6 | 赤下位2bit(PC4/PC5)は**TIM2_CC2→DMA1_CH7**で並行取得し、FWがbit2/6に合成 | 赤が3bit階調になる |
| V7 | 映像パケットは**EP4/EP1の2本のみ**に分散（1EP実効~3.3MB/s、必要4.6MB/s） | fps低下(~43fps) |
| V8 | USB送信バッファ(g_txpkt等)に**送信完了前に次データを書かない**（ステージング必須） | 全パケット1本ズレ→黒線 |

## 音声

| # | 不変条件 | 破った場合の症状 |
|---|---|---|
| A1 | タップは**SO1/SO2（プリボリューム）**。LOUT/ROUTはアンプ出力なので不可 | 本体音量に依存 |
| A2 | **RCフィルタ（1kΩ直列+10nF対GND）必須**。生PWMのADC直読みは3-4bit相当になる | 音がくぐもり爆音ノイズ |
| A3 | ADCは**32.768kHzの整数倍**（現在10倍=327.68kHz）でトリガし、**1キャリア周期分を箱型平均** | 15.2kHz等のピー音（キャリア折り返し） |
| A4 | ADCサンプル時間はトリガ周期に対し**余裕を持たせる**（現在13.5cyc、ペア2.9µs<3.05µs） | 取りこぼしによるノイズ |
| A5 | 音声パケットは**EP3専用**（単一EP=順序保証）。複数EPに分散禁止 | 時間シャッフルで激しい音割れ |
| A6 | **L/R: SO1=右, SO2=左**（gba-pantest ROMで実測確定） | 左右逆 |
| A7 | ホスト側入力レートはFW実レートに一致させる（現在32802Hz→WDLリサンプラで48kHz化） | バッファドリフトでプチプチ |

## USB/システム

| # | 不変条件 | 破った場合の症状 |
|---|---|---|
| S1 | IAP(0x08000000,16KB) + APP(0x08004000, app_offset.ldでリンク)。BKPマジック0x424C | 手放し書き込み崩壊 |
| S2 | **WWDG絶対禁止**（純正ISP ROMが食わせないため救済不能になる）。IWDGは可(使用中) | 文鎮化リスク |
| S3 | IWDGは**mainの最初**に開始（初期化ハングからも復帰させる） | ハングで沈黙(USB非列挙) |
| S4 | ADCキャリブレーション等の busy ループには**タイムアウト必須** | 同上 |
| S5 | ウィンドウスタイル変更はドラッグのモーダルループ内で**同期実行しない**（BeginInvoke） | ビューア表示崩れ |

## 追記 2026-10-18: パケット長を 484B → 512B に変更(FW v0.34)

**変更理由**: ESP32-P4 録画機の USB ホストは、484B のショートパケットごとに転送完了の
処理(1 万回/秒)が走り、core0 の 6〜7 割を使っていた。512B(バルク EP の最大パケット長)に
詰め物 28B(0)を足してショートパケットをなくし、ホストが 4KB の転送でまとめて受け取れるようにした。

**変わらないもの**: V7(映像は EP4/EP1 の 2 本、音声は EP3 専用)と V8(送信完了前に
次データを書かないステージング)はそのまま。パケットの中身(ヘッダ 4B + 240×u16)も v3 のまま。
受け手(PC ビューア・CLI・録画機)はマジックで 512B ずつ切り出す。

nano を PC に接続して再検証した結果(2026-10-18)は次のとおり。

| 検証 | 結果 |
|---|---|
| `dotnet test`(C# 18 件) | green(testhost が起動できない環境だったため反射で全 Fact を実行) |
| `freq` | DCK 2317229/s、LP 13618/s、SPL 9615/s。v0.33 と同じ |
| `framestat` | last=241 min=241 max=241。v0.33 と同じ(ダミー 1 バーストぶん) |
| `capture` | 160 ライン欠落 0。画像正常 |
| `streamtest` | 5.31MB/s(EP4 4.39 + EP1 0.56 + EP3 0.36)。160 ライン全部観測。帯域は 484B 時の +5.8% |
| ビューア | 下記 |

`framestat` の 'Q' 応答は 512B のストリームに混ざって届くので、CLI 側は "GBACq" を探すように直した。

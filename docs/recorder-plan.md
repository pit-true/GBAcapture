# スタンドアロン録画デバイス — 確定要件と構成（2026-07-08 改訂2）

## 確定した要件

| # | 項目 | 回答 |
|---|---|---|
| 1 | 記録形式 | **mp4のみ（音声入り、4x=960×640、なるべく高画質）**。生データ保存はしない（容量と編集ソフトの扱いにくさのため不採用と決定） |
| 2 | 使用シーン | オフ会に持ち出して録画。小型重視 |
| 3 | 録画量 | ポケモン対戦を1日10試合程度。1試合最大30分、平均10分 |
| 4 | 電源 | **モバイルバッテリーからUSB Type-Cで給電**。LiPoバッテリー実装は今回やらない（共有基板 docs/photos/battery.png の再現・拡張は将来の基板化フェーズで） |
| 5 | ネットワーク | **Wi-Fiは使わない**。現地にWi-Fiは無い前提（時刻はRTCモジュールで持つ） |
| 6 | 音声 | 同録必須 |
| 7 | プレビュー | LEDのみ（対戦中は本体画面を見る） |
| 8 | 2WAY運用 | ケーブル挿し替えでPCビューア/録画機どちらでも使える（nanoのFW変更不要） |
| 9 | UVC化との順序 | 録画デバイス先行 |
| 10 | PC取り込み | SDカードをカードリーダーで読む（録画専用にexFATパーティションを切りWindowsから直接見えるようにする） |

## ボード選定 — なぜ Raspberry Pi Zero 2 W か

必要条件を整理すると、候補はほぼ自動的に絞られる:

1. **USB 2.0 High-Speedのホストポート**が要る（nanoから約5MB/s受ける）→ マイコン全滅
2. **H.264ハードウェアエンコーダが「Linuxドライバ込みで」使える**こと。
   960×640@60fpsのソフトウェアエンコードはこのクラスのCPUでは間に合わない。
   ここが最大の罠で、**SoCカタログに「エンコーダ搭載」とあってもLinuxから叩けない製品が大半**
3. 4x拡大+USB受信+書き込みを回せるCPU/RAM、国内入手性、情報量

### 候補比較（検討した全ボード）

| ボード | CPU / RAM | H.264 HWエンコード | 評価 |
|---|---|---|---|
| **Raspberry Pi Zero 2 W** | 4×A53 1GHz / 512MB | **VideoCore IV。メインラインカーネルのv4l2m2m対応で `ffmpeg -c:v h264_v4l2m2m` が無設定で動く** | ◎ 採用 |
| Pi Zero W（初代） | 1×ARMv6 1GHz / 512MB | 同上（エンコーダは同じ） | △ CPUが1コアで受信+拡大が不安、.NET 8がARMv6非対応でGbaCap流用不可 |
| **LicheePi Zero**（Sipeed, Allwinner V3s） | 1×A7 1.2GHz / **64MB内蔵** | SoCとしては搭載（V3sはアクションカム用）だが、**Linuxで使うにはベンダBSP/リバースエンジニアリング(CedarX)頼み** | △ 基板は魅力的な小ささだが、RAM 64MBとエンコーダドライバが研究課題級。入手もAliExpressのみ |
| Lichee RV（D1, RISC-V） | 1×C906 1GHz / 512MB | **エンコーダ非搭載**（HEVCデコードのみ） | ✕ ソフトエンコードは絶望的 |
| Radxa Zero（S905Y2） | 4×A53 1.8GHz / 1-4GB | **非搭載**（デコード専用SoC） | ✕ CPU力押しになりリスク大 |
| Orange Pi Zero 2W（H618） | 4×A53 1.5GHz / 1-4GB | SoCには載っているが**メインラインLinuxから使えない**（ベンダBSPのみ、情報僅少） | △ |
| Luckfox Pico Ultra等（Rockchip RV1106） | 1×A7 1.2GHz + NPU / 256MB内蔵 | 搭載、**ベンダSDK(RKMPI)経由で使える**。ドラレコ用SoCでハード適性は実は最高 | ○ 超小型・低電力・~2千円。ただしbuildroot+C/C++のベンダSDK開発で工数3倍以上、.NET不可、情報少。「2台目」や基板化版の題材としては面白い |
| 中古Androidスマホ+OTG | — | — | 参考: 画面・電池込みだが開発がAndroidアプリになり別世界 |

**Pi Zero 2 Wの決め手**: ①エンコーダがffmpeg一発で使える唯一の小型ボード
②.NET 8 (ARM64)が動くのでGbaCapライブラリ（パケット解析・フレーム組立）を無改造で流用できる
③スイッチサイエンス/KSY/秋月で普通に買える ④情報量が桁違い。
ご質問の**LicheePi Zeroは「ハードは足りるがソフトの崖が深い」**が正直な評価
（V3sのエンコーダを動かすこと自体が1プロジェクトになる。同系の崖を登るならRV1106の方が新しくて筋が良い）。

## 構成

```
GBA ──(既存タップ)── nanoCH32V305 ──USB OTG── Raspberry Pi Zero 2 W ── microSD
（GBA本体は普通に乾電池駆動）  (現行FW無変更)       65×30mm                (Pi内蔵スロット)
                                                    │ microUSB給電
                              モバイルバッテリー(Type-C出力) ──[C→microBケーブル]──┘
                              ボタン1個(録画開始/停止) + LED(録画中点灯) + RTC(DS3231)
```

- Wi-Fi/Bluetoothは運用では**無効化**（消費電力削減にもなる）
- Linux起動20〜30秒 → オフ会では朝1回起動しっぱなしで運用
- 電源断でSDが壊れないようルートFSはread-only化（録画パーティションのみ書込）。
  シャットダウンはボタン長押し

### 記録フォーマット — 「mp4でなるべく綺麗に」の中身

| 項目 | 設定 | 理由 |
|---|---|---|
| 解像度 | **960×640（4x・最近傍拡大してからエンコード）** | H.264の色情報は2×2画素共有(4:2:0)のため、240×160のまま圧縮するとドット輪郭が滲む。4x後なら1ドット=4×4画素で滲みが実質不可視になる |
| フレームレート | 59.73fps（ソースそのまま） | |
| ビットレート | **16Mbps目安**（HWエンコーダなので余裕。GBA映像は平坦領域が多く実質ほぼ無劣化） | 約2MB/s |
| 音声 | AAC 48kHz ステレオ（既存の32802Hz→48kHzリサンプルを流用） | |

- 容量: **平均10分試合=約1.2GB、最大30分=約3.6GB、1日10試合=約12〜15GB**
  → **microSD 64GBで足りる**（128GBなら数日分。OS領域含め64GB以上を推奨）
- 録画データは専用の**exFATパーティション**に置く → SDを抜いてWindowsのカードリーダーで
  そのまま読める。家ではnanoの代わりにPCへUSB接続してUSBマスストレージとして
  見せるモードも作れる（ケーブル1本、SD抜き差し不要の選択肢）

### 時刻（Wi-Fiなしでのファイル名対策）

**RTCモジュール（DS3231、I2C接続、数百円）**をGPIOに載せる。最初にPC経由で一度合わせれば
ボタン電池で数年保つ。これで `2026-07-12_13-05_match03.mp4` のような名前が現地で正しく付く。

### 電源（今回はモバイルバッテリー）

- 消費: Pi Zero 2 W録画中 約2〜2.5W + nano約0.5W = **5Vで約0.5〜0.6A**
  （GBA本体は自前の乾電池なので含まない）
- **10000mAhクラスなら1日余裕**（5000mAhでも6時間程度いける計算）
- ケーブルは Type-C出力→microB入力 の1本
- 注意点は1つだけ: **低負荷自動OFF機能付きのバッテリーだと待機中に切られる**ことがある。
  0.5A流れ続けるので大抵は大丈夫だが、現地投入前に手持ちのバッテリーで連続動作確認をする
- 将来の基板化では battery.png のLiPo基板に5V昇圧（TPS61023クラス）を足してPi給電に
  統合する（構想のみ。今回は対象外）

## 手持ち部品の扱い

- **K-05488（microSD SPI DIP化キット）**: 今回は出番なし（SPIは実効1〜2MB/sで足りず、
  Pi内蔵スロットを使うため）。将来のマイコン実験用に保管
- **ブレッドボード**: ボタン・LED・RTCの試作配線で使用

## 開発ステップ

1. 部品購入（上表）
2. Piセットアップ: Raspberry Pi OS Lite (64bit)。初期設定・パッケージ導入時だけ
   ネットが要るので**家でUSBガジェットモード（PCとUSB直結+接続共有）またはその場限りの
   手段で済ませる**。運用イメージに合わせ最終的にWi-Fi/BTは無効化
3. **疎通確認**: GbaCap.Cliをlinux-arm64向けにビルドし、Pi上で `freq` / `capture` が
   通ることを確認（プロトコル層がLinuxでそのまま動く証明。既存コード無変更）
4. 録画アプリ（TDD、ロジックはまずPC上でテスト）: 3EP受信→フレーム組立→4x最近傍拡大→
   ffmpegパイプ（h264_v4l2m2m 16Mbps + AAC）→試合単位のmp4分割
5. GPIOボタン/LED/RTC、systemd自動起動、ルートFS read-only化、録画用exFATパーティション
6. モバイルバッテリーで実測（連続録画時間・自動OFFしないか・発熱）
7. ケース（3Dプリント or 市販小型ケース）

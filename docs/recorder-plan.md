## 確定構成: Raspberry Pi Zero 2 W（旧・案A）

mp4（H.264）エンコードはCH32V305では原理的に不可能で、かつ生データ約5MB/sは
SPI接続microSD（実効1〜2MB/s）にも書き切れない。**ハードウェアH.264エンコーダと
高速SDスロットを持つ小型Linuxボード**が要件に対する最小解。

```
GBA ──(既存タップ)── nanoCH32V305 ──USB OTG── Raspberry Pi Zero 2 W ── microSD
                     (現行FW無変更)             65×30mm, ~¥3,500        (Pi内蔵スロット)
                                                 │
                              ボタン1個(録画開始/停止) + LED(録画中点灯)
```

- **サイズ**: 65×30mm。nanoと合わせてもフリスクケース級に収まる
- **プロトコル流用**: .NET 8がARM64 Linuxで動くため、GbaCapライブラリ（パケット解析・
  フレーム組立）をそのまま使った録画アプリが作れる。nano側は一切触らない（不変条件維持）
- **弱点と対策**: Linuxなので起動20〜30秒（オフ会では朝1回起動しっぱなしで運用）、
  電源断によるSD破損リスク（ルートFSをread-only化+長押しシャットダウンで対策）

### 記録フォーマット（「綺麗に残す」と「mp4が欲しい」の両立）

**生ストリームとmp4を同時保存する**（Pi Zero 2Wの書込帯域で両方賄える）:

| 出力 | 内容 | サイズ |
|---|---|---|
| 生データ（編集マスター） | 現行USBパケットをそのままファイル化。**ビットパーフェクト無劣化** | 約5MB/s = 3GB/10分試合 |
| mp4（すぐ見る/確認用） | H.264 HWエンコード **960×640(4x最近傍)@59.73fps** + AAC 48kHz、8〜12Mbps | 0.6〜0.9GB/10分試合 |

- 4x拡大を**エンコード前**にやるのが画質のポイント: H.264の色情報は2×2画素で共有される
  （4:2:0）ため、240×160のまま圧縮するとドット絵の輪郭が滲む。4xに拡大してから圧縮すれば
  1ドット=4×4画素になり滲みが実質見えなくなる
- 1日10試合（平均10分）≒ 生30GB + mp4 8GB → **microSD 128GB（UHS-I、A1以上）を推奨**
- PC取り込みはSDカードをカードリーダーで読むのが最速・確実。PC側に
  「生データ→無劣化系4x mp4」変換ツールを用意する（GbaCap.Cliに追加）
- 慣れてきて生データ不要と感じたら設定でOFFにして容量節約可

### 操作系

- タクトスイッチ1個: 短押し=録画開始/停止（試合ごとに1ファイル）、長押し3秒=安全シャットダウン
- LED: 消灯=待機 / 点灯=録画中 / 点滅=エラー（SD残量不足・信号ロスト等）
- ファイル名: 家のWi-FiでNTP同期した時計を保持（fake-hwclock）。オフ会（ネット無し）では
  多少ズレるが連番+日時で実用上問題なし
- 最大30分連続録画はファイルサイズ的にもFAT32の4GB制限（exFATを使うので実際は無関係）にも問題なし

## 電源設計 — 共有バッテリー基板の拡張

battery.png（KiCad回路図）の構成の読み取り:

| ブロック | 内容 |
|---|---|
| USBコネクタ・電源ライン | USB-C（5.1kΩ CC終端、5V受電専用） |
| リポ充電回路 | **BQ24073**（パワーパス方式: 充電しながらSYS-OUTへ給電可、充電/PGOOD LED付き） |
| 過放電防止 | AO3400A + 61CN30によるロードスイッチ（GBA-M側を遮断） |
| 降圧回路 | **TLV62130**降圧 + 61CN36 → GBA-P（GBA本体電源 2.1V/3.3V系） |
| パスコン | 100µF多数 |

つまりこの基板は「LiPo→GBA本体給電+USB-C充電」用。録画デバイス統合での**拡張ポイントは
5Vレールの追加**（Pi Zero 2 Wは5V入力必須。SYS-OUTはLiPo電圧3.0〜4.2Vのため直結不可）:

```
SYS-OUT(3.0〜4.2V) ──[追加: 5V昇圧 TPS61023クラス、実効1.5A]── Pi Zero 2 W 5Vin
                                                                └→ nano（PiのUSBから給電）
GBA-P ── GBA本体（従来どおり）
```

### 消費電力見積もりとバッテリー容量

| 負荷 | 概算 |
|---|---|
| Pi Zero 2 W（録画中） | 約2.0〜2.5W |
| nanoCH32V305（PiのUSB経由） | 約0.5W |
| GBA本体 | 約0.5W |
| 合計（昇圧効率90%込み） | **約3.5〜4W ≒ LiPo 3.7Vで約1A** |

オフ会1日（通電5〜6時間）なら **5000mAh級LiPo** が目安。手持ちのモバイルバッテリーが
あれば試作段階はそれで代用できる（USB-C入力に挿しておけばBQ24073のパワーパスで動く）。

### ブレッドボード再現の注意（先に知っておくべき唯一のハードル）

BQ24073（QFN-16）とTLV62130（QFN-16）は**足が出ていないパッケージ**なので、ブレッドボードには
**QFN→DIP変換基板に載せる実装作業（ホットエアかリフロー）が必要**。進め方の提案:

1. **録画系（Pi+nano+SD）を先にUSBモバイルバッテリー給電で動かす** — 電源回路と録画開発を
   分離でき、失敗要因を切り分けられる
2. 並行してQFN変換基板+部品を調達し、ブレッドボードで電源基板を再現（充電・過放電・昇圧の動作確認）
3. 将来の基板化では、この回路に「5V昇圧 + Pi Zero 2 W用ヘッダ（またはCM相当）+ nano接続」を
   足した拡張版を起こす

## 手持ち部品の扱い（正直な結論）

- **K-05488（microSD SPI DIP化キット）**: 今回の構成では**出番なし**。SPI接続は実効1〜2MB/sで
  生データ5MB/sに届かず、マイコン直書き案自体が成立しない（Pi内蔵のSDIOスロットを使う）。
  将来のマイコン実験用に保管
- **ブレッドボード**: 電源回路の再現と、ボタン/LED周りの試作で活躍する

## 開発ステップ

0. 部品購入（上表）
1. Piセットアップ: Raspberry Pi OS Lite (64bit)、SSH、家Wi-Fi、ffmpeg、.NET 8ランタイム
2. **疎通確認**: GbaCap.Cliをlinux-arm64向けにビルドし、Pi上で `freq` / `capture` が通ることを確認
   （= プロトコル層がLinuxでそのまま動く証明。ここまでは既存コード無変更）
3. 録画アプリ（TDDで、まずPC上でロジックをテスト）: 生ストリーム保存 → ffmpegパイプで
   同時mp4化（`h264_v4l2m2m`、4x最近傍拡大）→ 試合単位のファイル分割
4. GPIOボタン/LED、systemd自動起動、ルートFS read-only化（電源断耐性）
5. PC側変換ツール: 生データ→無劣化系4x mp4（GbaCap.Cliに `convert` 追加）
6. 電源統合（バッテリー基板再現→昇圧追加→実測で連続録画時間確認）
7. ケース（3Dプリント or 市販小型ケース）

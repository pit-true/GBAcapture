# 偽ころキャプチャ 仕様説明書 — 「どうやって作ったの？」に答えるための文書

## 30秒で説明するなら

> GBAの基板から液晶に送られている映像信号（RGB15bitのパラレルバス）と、CPUから出ている
> 音声信号を直接ハンダ付けで取り出して、小さなRISC-Vマイコン（CH32V305）でデジタルのまま
> 取り込み、USB経由でPCに毎秒60フレーム送っています。PC側は自作のビューアで表示して、
> 録画はOBSでウィンドウキャプチャするだけ。エミュレータではなく実機の出力そのものです。

## 全体構成

```
GBA実機 (AGB-CPU-02, 40ピン液晶の初期型)
 │ 基板裏の印字付きビア19本にハンダ付け（映像17本+音声2本+GND）
 ▼
nanoCH32V305 (WCH CH32V305RBT6, RISC-V 144MHz, USB High-Speed内蔵, ~1000円)
 │ USB 2.0 High-Speed (480Mbps) バルク転送
 ▼
Windows PC — 自作ビューア「GBAcapture (Nisekoro-capture)」(C#/.NET 8)
```

## ハードウェア仕様

### 取り出している信号（GBA基板の印字付きビアから）

| 信号 | 本数 | 内容 |
|---|---|---|
| DCK | 1 | ドットクロック 4.194MHz。**可視ピクセル区間だけ動くバーストクロック** |
| SPL | 1 | 可視ライン開始パルス（160回/フレーム） |
| LP | 1 | ラインラッチ（228回/フレーム、計測用） |
| LDR/LDG/LDB 1-5 | 15 | RGB各5bit のパラレルデータ |
| SO1 / SO2 | 2 | CPUの音声出力（**SO1=右, SO2=左**。音量ホイールの上流なので本体音量と無関係） |
| GND | 1 | **最重要**。P1-GND（通信ポートのGND）に接続 |

- 映像15bitのうち13bitはマイコンのGPIOポートB、2bit（赤下位）はポートCに接続
  （nanoCH32V305はPB2/PB6/PB7がヘッダに出ていない — B6/B7はUSB-HSの信号線そのもの）
- 音声2本は **1kΩ直列 + 10nF対GND のRCフィルタ**（fc≈16kHz）を通してADC入力へ。
  GBAの音声はPWM（矩形波のデューティに音が乗る方式）なので、平滑してからADCで読む

### 教訓として語れる話

- **GND1本がすべての前提**。開発中、19本の信号線が完璧でもGNDが「パネル電源のVSS」
  という0Vでない場所に繋がっていたため、全信号が「常時HIGH」に見えて数日悩んだ。
  電圧は2点間の差。基準を共有しない計測は全部無意味になる
- GBAの液晶コネクタには32ピンと40ピンの2世代があり、ピン配置が違う（+1シフト関係）

## ファームウェア仕様（C言語、ch32funフレームワーク、約900行）

### 映像取り込み — 「割り込みに頼らない」のが肝

1. DCK（ドットクロック）をタイマTIM2の入力キャプチャに入れ、**クロックの立ち下がり
   1回ごとにDMAがGPIOポートを1回読む**。CPUは介在しない（=ジッタが出ない）
2. DMAは**サーキュラ（リング）モードで起動時に1回だけ設定**。ライン毎の再設定はしない
   — 途中でUSB割り込み等と競合してタイミングが揺れ、絵が横に乱れるため（実際に踏んだ）
3. **フレームの頭出しはデータ自身から**: DCKは垂直帰線（VBLANK）中に約5ms止まるので、
   「DMAの進みが250µs止まったら、次のサンプルはライン0の先頭」と判定できる
4. 実測で判明した仕様: **1ライン周期はDCK 241パルス**（可視240 + 水平帰線中に1個の
   ダミーパルス）。241ストライドで区切らないと絵が対角線状にズレていく
5. 赤下位2bitは同じDCKエッジから第2のDMA（タイマの第2チャンネル経由）でポートCを
   並行読みし、FWが16bitワードの空きビットに合成する

### USB転送 — 独自プロトコル（UVCではない）

- ベンダー固有クラス。**ラインパケット484バイト**（ヘッダ4B: マジック0xA5/フレーム番号/
  ライン番号 + 240ピクセル×16bit）を1ラインごとに送る
- USB-HSバルクは**1エンドポイントあたり実効約3.3MB/s**しか出ない（NAK後のホスト再ポーリング
  がマイクロフレーム単位になるため）。映像は約4.6MB/s必要なので**EP2本に分散**、
  音声は順序が命なので**専用EP1本**（分散させると到着順が崩れて音が壊れる — 実際に踏んだ）
- コマンド（ping/キャプチャ/ストリーム開始停止/診断/更新）はEP5のバルクOUTで受ける

### 音声取り込み — キャリア同期積分

- GBAの音声PWMのキャリアは必ず32.768kHzの整数倍（SOUNDBIAS設定、GBATEKで確認）
- ADCを**327.68kHz（キャリアの10倍）でトリガし、ちょうど1周期分=10サンプルを平均**
  → 平均フィルタの零点がキャリアと全高調波に一致し、原理的にPWMノイズが消える
- 32.8kHzで送り、PC側で48kHzにリサンプリング

### 開発基盤 — ボタンフリー書き込み（IAP）

- CH32V30xは純正ブートローダへのソフト突入が不可能（ROMがBOOT0ピンのメモリマッピングに
  依存。ROM逆アセンブルまでして確認した）
- そこで**自前の16KBブートローダ（IAP）**をフラッシュ先頭に常駐させ、アプリは0x08004000に配置。
  「USBコマンド→バックアップレジスタにマジック→ソフトリセット→IAPが新FWをUSB受信して
  自己書き換え」で、**ボタンに触れず約10秒でFW更新**できる
- 暴走対策にウォッチドッグ（6.5秒）も常駐。以降の開発でボタンを押したのは数回だけ

## 処理の流れ詳解 — FWとホストはそれぞれ何をしているか

「1枚の絵と1秒の音がPCに届くまで」を、FW→ホストの順に追った説明。
（コードの詳細ではなくロジックの説明。実装は firmware/app/gbacap_app.c と host/GbaCap*）

### FW側（nanoCH32V305の中で起きていること）

役割を一言で言うと **「信号のサンプリングはハードウェアに丸投げし、CPUは
『リングバッファのどこからどこまでが何ライン目か』の計算と梱包だけをやる」**。

1. **取り込みはCPU不介在**: DCK（ドットクロック）の立ち下がりごとに、タイマ経由で
   DMAが2本同時に走り、GPIOポートB（13bit分）とポートC（赤下位2bit）を各1回読んで
   リングバッファに書く。リングは7712サンプル=ちょうど32ライン分で、**ストリーム開始時に
   1回設定したら止めない**（サーキュラ）。以降、映像データは勝手に貯まり続ける
2. **メインループはDMAの書き込み位置だけを監視**している。位置が250µs進まなくなったら
   「いまVBLANK（垂直帰線）に入った」= **次に書かれるサンプルはフレーム先頭**と分かるので、
   そこをアンカー（フレーム基準位置）にする
3. ただしVBLANK中に**SPLを伴わないダミーの1バースト**が入るため、アンカーだけだと
   1ライン分ずつ巻き取りがズレていく。そこで**フレーム先頭のSPL（ライン同期パルス）が
   来た瞬間のリング位置**を割り込みで記録しておき、アンカーとの差が「241の整数倍」から
   外れていたら241単位で補正する（ハイブリッドアンカー）
4. アンカーから**241サンプル刻み**でラインを切り出す。各ラインの先頭1サンプルはジャンク
   なので**+1オフセットから240個**を採用。ポートB由来の13bitとポートC由来の2bitを
   1ピクセル16bitに合成する
5. 240ピクセル+ヘッダ4バイト（マジック0xA5・フレーム番号・ライン番号）=484バイトの
   パケットを**ステージングバッファに組み立ててから**USBへ渡す。送信完了前のバッファを
   絶対に触らない（触ると全パケットが1本ズレて黒線が出る）。映像はEP4とEP1へ交互に投げて
   帯域を稼ぐ
6. **音声は完全に別系統**: タイマがADCを327.68kHz（PWMキャリアのちょうど10倍）で
   自動トリガし、DMAが貯める。メインループが**10サンプルずつ箱型平均**して32.8kHzの
   L/R1組に潰す（この平均でPWMキャリアが原理的に消える）。48ペア貯まるごとに
   0xA6パケット（シーケンス番号付き）にして**EP3専用**で送る
7. 以上の合間に、EP5から来るコマンド（ストリーム開始/停止・静止画・診断・FW更新）を
   処理し、ウォッチドッグに餌をやる。フレームバッファは持たない（RAM32KBに入らない）
   — **「ライン単位で切り出して即送る」がFWの全て**

### ホスト側（PCの中で起きていること）

役割を一言で言うと **「バラバラの順番で届く484Bパケットを、ヘッダの座標情報だけを頼りに
絵と音に並べ直す」**。

1. **3つのINエンドポイントを並行に読む**受信ループが回る（EP4/EP1=映像、EP3=音声）。
   受信データを484バイト単位に切り、先頭マジック（0xA5/0xA6)で映像/音声を判別してパース
2. **映像の再組み立て**: 2本のEPに分散した結果、パケットの到着順はぐちゃぐちゃになる。
   しかし各パケットが「フレーム番号・ライン番号」を自己申告しているので、
   フレームアセンブラは**届いた順に関係なく正しい位置へ置くだけ**でよい。
   160ライン揃ったらそのフレームを確定する（欠落はカウントされ診断コマンドで見える）
3. 確定フレームを15bit RGB→24bit RGBにデコードし、ビューアが**整数倍の最近傍拡大**
   （ドットをぼかさない）で描画する。一定時間パケットが来なければNO SIGNAL表示に切り替え
4. **音声の再生**: 0xA6パケットのシーケンス番号で欠落を検知しつつL/Rサンプルを
   リングバッファへ積む。FWの実レート32802Hzから48kHzへ**リサンプラ（WDL）**で変換して
   WASAPI共有モードに流す。レートを「32768Hzのはず」と決め打ちせず実測値に合わせるのが
   ポイントで、ズレるとバッファが徐々に溜まる/枯れるかしてプチプチ言い出す
5. 既定の出力デバイス変更（イヤホン抜き差し等）を検知したら音声出力を作り直して追従。
   F12で表示中の確定フレームをPNG保存（`ピクチャ\GBAcapture\`）

### 分担の設計思想

- **時間に厳しい処理（サンプリング・同期）は全部FW側**。ハードウェア任せにできる形へ
  問題を変形するのがFWの仕事で、CPUが1サンプルずつ触る設計は最初から捨てている
- **メモリと計算力が要る処理（フレーム組み立て・拡大描画・リサンプル）は全部ホスト側**。
  FWはフレームを1枚も持っていない
- 両者の界面は「自己記述的な484Bパケット」だけ。だから受け側はPCでもLinuxボードでも
  よく、録画デバイス計画（recorder-plan.md）はこの性質に乗っている

## トラブル年表（聞かれたら面白い話）

1. **全信号が沈黙** → GNDがパネル電源VSSに繋がっていた（基準電位の欠落）
2. **純正ブートローダにソフトで入れない** → ROM逆アセンブルで「不可能」を確定し、IAP自作へ
3. **黒い横線** → USB送信バッファを送信完了前に上書きしていて全パケットが1本ズレていた
4. **右端の白い縦線・対角線ノイズ** → 「1ライン=240クロック」という思い込み。実は241
5. **映像の水平ジッタ** → ライン毎のDMA再アーム（割り込み競合）。サーキュラDMA化で根治
6. **音割れ** → 音声パケットを複数EPに分散して順序が崩れていた
7. **ピー音** → PWMキャリア32.768kHzが48kHzサンプリングとの差分15.2kHzに折り返していた
8. **こもった音** → PWM矩形波を数点のADCサンプルで読むこと自体が3-4bit量子化。RCフィルタで解決
